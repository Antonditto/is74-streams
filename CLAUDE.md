# is74-streams — контекст проекта

## Цель проекта

Есть сервис `old-stream.is74.ru` (Интерсвязь, оператор ШПД/видеонаблюдения в Кургане/Челябинске
и др.) — веб-портал для просмотра дворовых камер и домофонов, привязанных к личному кабинету
жителя. Задача: сделать сервис, который:

1. Авторизуется в API Интерсвязи (по номеру телефона + push/SMS-код),
2. Получает список доступных камер и прямые ссылки на потоки,
3. Отдаёт эти потоки в **go2rtc** (а через него — в **Frigate** и Home Assistant) в виде
   стабильных RTSP/WebRTC-эндпоинтов, не завязанных на протухающие токены со стороны Frigate.

Конечная цель — Docker-сервис + Home Assistant add-on.

## Владелец задачи / окружение

Автор — DevOps-инженер, обширный self-hosted homelab (Proxmox, Rancher/RKE2 Kubernetes, Docker
single-node, GitLab с CI/CD, Harbor, Traefik, AdGuard Home, Keycloak, стек мониторинга
Prometheus/Grafana/Loki/Alertmanager). Наработан опыт с go2rtc-подобными интеграциями, Home
Assistant/ESPHome. Данный проект — часть homelab, не production-инфраструктура компании.
Предпочтение — Go для сервисов (соответствует остальному стеку), но конкретно для этой задачи
хватило Python-скрипта и штатного образа go2rtc.

## Реверс-инжиниринг API Интерсвязи (из HAR-дампа браузера)

Портал `old-stream.is74.ru` — React SPA, работает с несколькими бэкендами:

### 1. Авторизация — `api.is74.ru`

Три последовательных запроса (флоу "вход по номеру телефона + код из push/SMS"):

```
POST https://api.is74.ru/mobile/auth/send-push-code
Body: {"phone":"9XXXXXXXXX","uniqueDeviceId":"<случайный hex-id устройства>"}
Response: {"authId":"<uuid>","message":"На номер +7 (9XX) XXX-XX-XX отправлен пуш-код подтверждения в МП"}
```

```
POST https://api.is74.ru/mobile/auth/confirm
Body: {"confirmCode":"XXXX","phone":"9XXXXXXXXX"}
Response 200: {"authId":"<тот же uuid, что и в send-push-code>","message":"Телефон подтвержден",
               "addresses":[{"USER_ID":"XXXXXXXX","ADDRESS":"Город, мкр. ..."}, ...]}
Response 422 (неверный код): [{"field":"confirmCode","message":"Неверный код подтверждения"}]
```

Важно: `userId` для следующего шага — это **не** плоское поле ответа, а `addresses[0].USER_ID`
(один номер телефона может быть привязан к нескольким адресам/лицевым счетам — в `app/main.py`
сейчас просто берётся первый). `authId` при этом один и тот же что в `send-push-code`, что в
`confirm` — можно брать из любого из двух ответов.

```
POST https://api.is74.ru/mobile/auth/get-token
Body: {"authId":"<из send-push-code/confirm>","uniqueDeviceId":"<тот же id>","userId":"<addresses[0].USER_ID>"}
Response (реально получен, структура):
{
  "USER_ID": 00000000,
  "PROFILE_ID": 0000000,
  "APP": "mobile",
  "ACCESS_BEGIN": "2026-08-14 01:41:49",
  "ACCESS_END": "2027-08-14 01:41:49",
  "TOKEN": "<32-символьный hex>",
  "AUTH_TYPE": "phone",
  "UNIQUE_DEVICE_ID": "<тот же id>",
  "REMOTE_ADDR": "<ip клиента на момент выдачи>",
  "PHONE": 9XXXXXXXXX,
  "LAST_CHECK_DATE": "2026-08-14 01:41:49",
  "ACCESS_END_LEFT": 31536000
}
```

**Важно: `ACCESS_END_LEFT` = 31536000 секунд = ровно 1 год.** Токен живёт год с момента выдачи.
Это радикально упрощает архитектуру — **не нужен фоновый сервис для рефреша токена**. Авторизацию
(с ручным вводом кода подтверждения) можно проходить руками раз в год через веб-форму `/login`
сервиса.

Открытый вопрос (не проверено): протухает ли токен раньше срока при долгом бездействии, и есть ли
способ продлить его автоматически без прохождения confirm-флоу заново. Пока считаем, что нет.

**Важно про формат авторизации — два разных места:**
- JSON API (`cams.is74.ru/api/*`) — обычный HTTP-заголовок `Authorization: Bearer <TOKEN>`.
- Готовые CDN-ссылки (`cdn.cams.is74.ru/snapshot`, `.../hls/...`, `wss://.../ws/mse`) —
  query-параметр `token=bearer-<TOKEN>` **внутри самой ссылки**, которая уже приходит в таком
  виде в ответе `limited-info`. Собирать эти ссылки вручную не нужно — сервер отдаёт их готовыми.

### 2. Список камер — `cams.is74.ru/api/get-group`

Эндпоинт "мои камеры" — им пользуется пикер "По имени" на `old-stream.is74.ru` (вкладка рядом с
"По адресу"), просто он называется не "мои камеры", а "группы":

```
GET https://cams.is74.ru/api/get-group/?selfCams=true
Response: [{"OBJECT":"GROUP","ID":"own","NAME":"Свои камеры"},
           {"OBJECT":"GROUP","ID":14575,"NAME":"<название группы>"}, ...]
```

Корневой список групп аккаунта: `own` (камеры, официально зарегистрированные на аккаунт) плюс
группы, которые Интерсвязь **сама привязала к аккаунту** (не пользовательские плейлисты —
пользователь их не создаёт, не переименовывает и не может поменять их состав из личного
кабинета, это фиксированный набор от провайдера). `own` + эти группы в сумме дают полный список
камер, доступных аккаунту — то есть это и есть настоящий источник исходного списка (раньше
такого прямого эндпоинта как будто не было видно, и список собирали вручную).

```
GET https://cams.is74.ru/api/get-group/{id}
Response: [{"OBJECT":"CAMERA","ID":...,"NAME":"..."}, ...]   // id = "own" или число
          или [{"OBJECT":"GROUP","ID":...,"NAME":"..."}, ...] — если id ведёт ещё на уровень
          вложенности (так устроено публичное дерево "Улицы Онлайн", см. ниже)
```

Публичное дерево городов ("Улицы Онлайн", `id=16`) — та же ручка: `get-group/16` отдаёт список
городов (`OBJECT: GROUP`), `get-group/<city-id>` — уже городские камеры (`OBJECT: CAMERA`, но
чужие, не личные — это открытые городские камеры, не привязанные к конкретному аккаунту).

ID из ответа группы (для `CAMERA`-элементов) дальше идут в `limited-info` за полной информацией
(`UUID`, ссылки и т.д.):

```
POST https://cams.is74.ru/api/limited-info
Body: {"CAMERA_IDS":[71069,71070,...]}
Response: объект { "<camera_id>": {...}, ... }
```

Реализовано в `is74_client.py` (`get_group`), эндпоинты сервиса — `GET /api/my-groups`
(корневой список) и `GET /api/group-cameras?group_id=` (камеры/подгруппы внутри). Проверено и
офлайн на реальных пейлоадах из HAR, и живьём на настоящем аккаунте.

(**Раньше в поиске "мои камеры" использовался другой путь** — автокомплит адреса
`simple-address.is74.ru/simple/search` + `cams.is74.ru/api/cams-with-address-object`, с ручным
вводом ID через drill-down по цепочке город → улица → дом → подъезд. Он честно работал, но
`get-group` оказался и надёжнее (без нечёткого текстового поиска), и показывает ровно то, что
действительно доступно аккаунту, а не вообще все дома в городе — этот путь целиком убран из
сервиса вместе с функциями `address_search`/`cams_with_address_object` и роутами
`/api/address-search`/`/api/address-cameras`. Если понадобится снова — контракт был:
`lastObject[name]`/`lastObject[id]` для сужения цепочки `region → area → city → locality → plan
→ street → building → porch → flat`, ответ `cams-with-address-object` — `{"cameras": {...}}` или
`{"error": "cameras found 0"}`, если камер нет.)

Структура одной камеры (реальный пример, значения адреса/UUID заменены на условные):

```json
{
  "ID": 71479,
  "UUID": "a1b2c3d4-e5f6-47a8-9b0c-d1e2f3a4b5c6",
  "NAME": "Двор, вид на детскую площадку",
  "STREAM_EXISTS": true,
  "SLEEP_MODE": false,
  "ADDRESS": "Город, мкр. N-й, д. XX, п. Y",
  "ACCESS": {
    "LIVE": {"STATUS": true, "REASON": ""},
    "ARCHIVE": {"STATUS": true, "REASON": "", "AUDIO": true},
    "DOWNLOAD": {"STATUS": false, "REASON": "..."}
  },
  "MEDIA": {
    "SNAPSHOT": {
      "LIVE": {
        "MAIN":  "https://cdn.cams.is74.ru/snapshot?uuid=<uuid>&token=bearer-<token>",
        "LOSSY": "https://cdn.cams.is74.ru/snapshot?uuid=<uuid>&lossy=1&token=bearer-<token>"
      }
    },
    "HLS": {
      "LIVE": {
        "MAIN":         "https://cdn.cams.is74.ru/hls/playlists/multivariant.m3u8?uuid=<uuid>&token=bearer-<token>",
        "LOW_LATENCY":  "https://cdn.cams.is74.ru/hls/playlists/multivariant.m3u8?uuid=<uuid>&realtime=1&token=bearer-<token>"
      },
      "ARCHIVE": "https://cdn.cams.is74.ru/hls/playlists/multivariant.m3u8?uuid=<uuid>&token=bearer-<token>"
    },
    "MSE": {
      "LIVE": "wss://cdn.cams.is74.ru/ws/mse?uuid=<uuid>&token=bearer-<token>"
    }
  }
}
```

Где что взять для go2rtc:
- **`UUID`** — идентификатор потока на CDN (не путать с `ID` — числовым id камеры в личном кабинете).
- **`NAME`** — человекочитаемое название (кириллица, требует транслита для использования в
  RTSP-путях/именах потоков go2rtc).
- **`MEDIA.HLS.LIVE.MAIN`** — то, что реально тащим в go2rtc.
- Также доступны: WebSocket MSE-поток (`MEDIA.MSE.LIVE`, `wss://.../ws/mse`) и снэпшоты
  (JPEG, `MEDIA.SNAPSHOT.LIVE.MAIN/LOSSY`) — пока не используются, но могут пригодиться:
  MSE — как альтернативный источник с меньшей задержкой, снэпшоты — для превьюшек в UI/HA.

### 3. Сам видеопоток — `cdn.cams.is74.ru`, обычный HLS

Подтверждено live-трафиком из HAR:

```
GET https://cdn.cams.is74.ru/hls/playlists/multivariant.m3u8?uuid=<uuid>&token=bearer-<token>
    → мастер-плейлист (application/vnd.apple.mpegurl)
GET https://cdn.cams.is74.ru/hls/playlists/ts.m3u8?quality=main&uuid=<uuid>&token=bearer-<token>
    → медиа-плейлист с сегментами
GET https://cdn.cams.is74.ru/<...>/<uuid>_main_<ts>_<seq>.ts/<signed-hash>?i=<user_id>&ik=<key>
    → сами TS-сегменты (video/mp2t), ссылки уже подписаны и вшиты в плейлист, отдельно токен
      к ним прикладывать не нужно
```

Никакой экзотики — это то, что умеет проигрывать любой HLS-плеер/ffmpeg "из коробки".
`quality=main` — судя по всему, есть и `sub` (более низкое разрешение) — не проверялось,
но по аналогии с `REALTIME_WS.sub`/`REALTIME_WS.main` в ответе `limited-info`, вероятно, тоже
доступно через `?quality=sub`.

### Прочие наблюдения по HAR

- Все запросы к `cams.is74.ru`/`cdn.cams.is74.ru` шлются с `Origin: https://old-stream.is74.ru`.
  CORS-заголовки в ответах разрешают `*` (для snapshot/hls) — то есть по идее заголовок Origin
  не проверяется на бэкенде так строго, как можно было бы ожидать, но это **не проверено вне
  браузера** (curl/ffmpeg). Если при первом тесте будет 403 — первое, что проверять: не требуется
  ли `Referer: https://old-stream.is74.ru/`.
- Плейлист `ts.m3u8` явно перезапрашивается каждые ~15 секунд (это стандартное поведение
  HLS-плеера для live, не специфика Интерсвязи).

## Архитектурное решение

Изначально предполагался auth-sidecar с фоновым рефрешем токена — **отменено**, т.к. токен живёт
год. Также отменён вариант офлайн-генератора `streams.yaml` — вместо него нужен постоянно
работающий веб-сервис, упакованный как **Home Assistant add-on**, со своей страницей входа
(вместо ручного похода в DevTools раз в год). Итоговая архитектура:

```
                        браузер → страница входа сервиса (/login, /confirm)
                                        │  send-push-code → confirm → get-token
                                        ▼
                          TOKEN (год жизни) → /data/state.json
                          (персистентное HA Supervisor-хранилище add-on'а,
                           входит в бэкапы HA; локально — volume ./data)
                                        │
                                        ▼
                    [is74-streams service, app/] ── GET /streams (HTML) ── человек
                                        │
                                        └────────── GET /api/streams (JSON, ссылки без токена) ──→
                                                     [go2rtc, отдельный HA add-on] ──RTSP/WebRTC/
                                                     MJPEG──→ Frigate / HA
```

- **`app/`** — сервис на Python/FastAPI: `main.py` (роуты), `is74_client.py` (httpx-обёртка над
  api.is74.ru + cams.is74.ru, включая транслит/слаг имён камер), `storage.py`
  (`/data/state.json`), `templates/` (Jinja2: login, confirm, settings, streams).
- ID камер личного кабинета собираются на `/settings` — через дерево `get-group` ("Мои группы")
  либо руками (см. раздел "Список камер" выше).
- **Ссылки на потоки не содержат токена Интерсвязи.** `hls_url`/`snapshot_url` в `/streams` и
  `/api/streams` указывают не на `cdn.cams.is74.ru`, а на собственные прокси-роуты сервиса —
  `GET /media/{camera_id}/multivariant.m3u8`, `.../ts.m3u8`, `.../snapshot` (`main.py`). Сервис
  сам подставляет реальный токен при обращении к CDN, а наружу (в go2rtc/браузер) отдаёт только
  свои URL. Мастер-плейлист переписывается так, чтобы ссылка на медиаплейлист вела обратно на
  наш `/media/.../ts.m3u8` (без токена); ссылки на сами `.ts`-сегменты внутри медиаплейлиста
  трогать не нужно — они уже подписаны отдельной схемой (`i=`/`ik=`), не токеном аккаунта, их
  просто делаем абсолютными (полный `https://cdn.cams.is74.ru/...`). Доступ к прокси
  дополнительно ограничен: `camera_id` должен быть в сохранённом `state.camera_ids`, иначе 403 —
  чтобы прокси не превращался в открытый релей токена аккаунта на произвольные UUID. Это и есть
  та самая "стабильность, не завязанная на протухающие токены", которая изначально задумывалась
  для go2rtc (см. "Цель проекта") — реализована на уровне этого сервиса, а не самого go2rtc.
- **go2rtc — отдельный HA add-on**, не входит в этот репозиторий. Он должен сам забирать
  актуальные ссылки на потоки из `GET /api/streams` этого сервиса (формат — плоский JSON-список
  камер: id/uuid/name/address/slug/hls_url/snapshot_url — все ссылки уже без токена).
- Раз в год (или когда токен протухнет) — зайти на `/login` этого сервиса и пройти push-auth
  флоу заново через веб-форму.

- [x] Веб-сервис `app/` (FastAPI) — полный флоу: `/login` → `/confirm` → `/settings` → `/streams`
      (HTML) + `/api/streams` (JSON для go2rtc/Frigate). Токен и список камер — в
      `/data/state.json` (см. "Архитектурное решение").
- [x] **`/settings`** — основной способ набрать список камер: секция "Мои группы" (плитки,
      кликабельный breadcrumb, drill-down по дереву `get-group`, "Выбрать все"/"Добавить все
      доступные камеры" — собирает `own` + все группы аккаунта, кроме публичного дерева "Улицы
      Онлайн"), плюс ручной ввод ID как запасной путь (принимает как `123, 456`, так и вставленный
      из `localStorage` массив `[123,456]`). Список камер — карточки с реальными превью,
      drag-and-drop для порядка (2D-сравнение по центру карточки, не только по Y — типовой Y-only
      алгоритм не работает в CSS grid с несколькими колонками), кнопки удаления/"Удалить все" (с
      подтверждением), круговой спиннер на время загрузки превью новых камер
      (`GET /api/camera-preview` — отдаёт снэпшот как `data:` URI в JSON, с retry на сам снэпшот
      и отдельной кнопкой "повторить" на карточке, если не подтянулся). Порядок карточек = порядок
      вывода на `/streams`/`/api/streams` (`build_stream_list(..., order=state.camera_ids)`).
      Поиск по адресу (`simple-address.is74.ru`) был реализован и затем полностью убран — не
      показывал ничего сверх того, что даёт `get-group`, но менее надёжно (нечёткий текстовый
      поиск); контракт задокументирован в разделе API выше на случай, если понадобится вернуть.
- [x] **`/streams`** — карточная сетка камер (SVG-спрайт иконок по типу камеры в
      `app/static/icons.svg`, классификация по ключевым словам в имени —
      `is74_client.camera_icon()`), кнопки копирования HLS/снэпшот-ссылок (`app/static/copy.js`,
      всплывающий тост вместо смены текста кнопки — не сдвигает карточку; fallback на
      `document.execCommand`/выделяемое поле без secure context), 3-режимный переключатель темы
      (auto/light/dark, persist в `localStorage`).
      **Замечание о совместимости**: поле `icon` в `/api/streams` — id символа в спрайте
      (`"ic-door"`), не эмодзи — если появятся внешние потребители JSON помимо go2rtc, это стоит
      иметь в виду.
- [x] **Ссылки на потоки без токена** — `hls_url`/`snapshot_url` указывают на собственные
      `/media/{camera_id}/multivariant.m3u8|ts.m3u8|snapshot` (см. "Архитектурное решение"),

## Работа за Traefik / HA Ingress

Реализовано через `ProxyAwareMiddleware` в `app/main.py` — единый ASGI-middleware, срабатывает
до роутинга: читает `X-Ingress-Path` (ставит HA Supervisor) → пишет в свой ключ
`scope["is74_prefix"]` (**не** в `scope["root_path"]`, см. гочтя ниже); читает
`X-Forwarded-Proto`/`X-Forwarded-Host` (Traefik подставляет их сам, без доп. конфигурации) →
правит `scope["scheme"]` и `Host`-заголовок. Свои хелперы — `_ctx`/`_redirect`/
`_public_base_url` — читают `is74_prefix` и вручную приклеивают его к путям/`str(request.base_url)`
(тот уже учитывает подправленные scheme/Host, но не Ingress-префикс — намеренно). Без заголовков
(прямой доступ по опубликованному порту) поведение не меняется. Заголовкам доверяем безусловно,
без allow-list доверенных прокси — осознанное упрощение для контекста приватного homelab, не для
публичного edge с недоверенными клиентами.

**Гочтя, стоивший реального 404 на проде (v0.0.1→0.0.2 фикс редиректов не помог до конца, добито
в 0.0.3)**: изначально Ingress-префикс писался прямо в `scope["root_path"]` — это ASGI-поле,
которое **сама Starlette использует для роутинга**, а не только для генерации URL. Starlette
0.46 (`get_route_path()`) ожидает, что `scope["root_path"]` — буквальный префикс `scope["path"]`
(WSGI-конвенция SCRIPT_NAME+PATH_INFO: прокси форвардит ПОЛНЫЙ путь, включая префикс, а
приложение само его срезает). У нас же HA Supervisor **уже срезает** Ingress-префикс до того, как
запрос попадёт к аддону — `scope["path"]` префикса не содержит. Из-за этого несовпадения
`Mount.matches()` (наш `/static`, смонтированный `StaticFiles`) при вычислении `root_path` для
дочернего приложения складывает старый (не совпадающий) `root_path` с совпавшим куском пути —
получается мусорное значение, `get_route_path()` внутри `StaticFiles.get_path()` не может его
срезать, и файл ищется по неверному относительному пути → 404. Обычные (не через `Mount`) роуты
вроде `/login`/`/streams` это не задевает — поэтому HTML успешно грузился, а `/static/app.css`,
`/static/icons.svg`, `/static/copy.js` — нет (симптом был обнаружен пользователем на реальном
HA: страница рендерилась, но совсем без стилей). Изолированный репро — голый Starlette `Mount` +
`StaticFiles` + миддлварь, ставящая `scope["root_path"]` в непустое значение, не совпадающее с
`scope["path"]`, — воспроизводит 404 в одну функцию, без FastAPI/Ingress вообще. Фикс: никогда не
писать в `scope["root_path"]` для этого сценария (Supervisor/большинство reverse-proxy со
strip-prefix уже срезают путь сами) — вести префикс отдельным ключом scope и строить ссылки
вручную, не полагаясь на встроенный в Starlette механизм root_path-роутинга.

Два независимых, не пересекающихся механизма:

- **Traefik перед сервисом** (без Ingress) — ничего специально настраивать не нужно: Traefik
  сам добавляет `X-Forwarded-Proto`/`X-Forwarded-Host` на обычном роутинге, сервис их подхватит
  и абсолютные ссылки на потоки (`hls_url`/`snapshot_url` в `/streams` и `/api/streams`) будут
  указывать на публичный Traefik-домен, а не на внутренний host:port контейнера. Собственная
  навигация сервиса (страницы, статика — root-relative через `{{ base_path }}` в шаблонах и
  `window.BASE_PATH` в JS) при этом работает независимо от домена.
- **HA add-on с Ingress** — Supervisor сам ставит `X-Ingress-Path`, `config.yaml` уже содержит
  `ingress: true`/`ingress_port`/`panel_icon`/`panel_title` (кнопка в боковой панели HA). Вся
  навигация сервиса подстраивается под динамический префикс `/api/hassio_ingress/<token>/`.
- **`IS74_INTERNAL_BASE_URL`** (env, в HA — опция `internal_base_url` через `run.sh`) —
  опционально, если консьюмеры (go2rtc/Frigate) стоят на том же хосте, что и этот сервис
  (типичный случай для HA add-on): `/api/streams` тогда отдаёт ссылки на этот internal-адрес,
  а `/streams`/`/settings` (человеку в браузере) всегда используют публичный `base_url`. Без
  переменной `/api/streams` отдаёт то же, что и `/streams`. **Не проверено вживую**, какое
  DNS-имя аддон реально получает в сети `hassio` — опция даёт способ задать его вручную.

## Переименование проекта: работа с bind-mount в devcontainer

Проект и репозиторий один раз переименовывались (была опечатка в исходном имени папки). При
переименовании обнаружился и был задокументирован важный для этого devcontainer'а гочтя:
**`docker compose` внутри devcontainer-песочницы через docker-outside-of-docker шлёт хостовому
dockerd bind-mount source как абсолютный путь в том виде, в котором его видит песочница**
(`/workspaces/<имя-папки>/data`), а не как реальный путь на диске хоста. Хостовый dockerd такого
пути не знает и просто молча создаёт по нему пустую директорию на своей файловой системе (внутри
VM Docker Desktop), если её там ещё нет. Работает только потому, что при повторных
`docker compose up`/`build` из той же папки путь совпадает со строкой, под которой каталог уже
был создан и populated в прошлый раз — если путь хоть немного меняется (переименование папки,
другой контекст запуска), `/data` внутри нового контейнера окажется пустым, а реальные данные
останутся лежать по старому пути на файловой системе VM (не удаляются, просто "уезжают").

Рецепт восстановления, если это повторится (нужны оба пути — старый и новый):
```
docker run --rm \
  -v /workspaces/<старое-имя>/data:/old \
  -v /workspaces/<новое-имя>/data:/new \
  alpine sh -c "cp -a /old/. /new/"
```
`docker rm`/`docker stop`/`docker network rm` не трогают данные на диске VM — они остаются, пока
их явно не удалить такой же командой с bind-mount'ом на этот путь.

Заодно: история сессий Claude Code и файлы памяти (`~/.claude`) не были примонтированы с хоста —
жили только в writable-слое конкретного контейнера devcontainer'а, поэтому пересоздание
контейнера (переименование папки, обычный "Rebuild Container") стирало бы всё. Исправлено —
`.devcontainer/devcontainer.json` монтирует `/home/vscode/.claude` как именованный docker-volume
(не привязанный к имени папки, чтобы будущие переименования его не задевали), и devcontainer сам
получил фиксированное имя контейнера через `runArgs: ["--name=..."]` вместо случайного.

## Важно про секреты и приватность

- **Не коммитить** в репозиторий: `TOKEN`, номер телефона, `uniqueDeviceId`, содержимое
  `data/state.json` (в нём токен и ID камер — по ID камер потенциально можно узнать реальные
  адреса через `limited-info`).
- `data/` (локальное персистентное состояние, аналог `/data` в HA add-on) — в `.gitignore`.
  В реальном HA add-on `/data` монтируется Supervisor'ом автоматически и в репозиторий не попадает
  по определению (это runtime-директория контейнера, не часть git-дерева).
- HAR-дампы браузера (`*.har`) — тоже в `.gitignore`: в них реальный токен, телефон, адреса камер.
- Секреты — только в `/data/state.json` (рантайм), не в коде и не в issues/PR-описаниях. Если
  понадобится CI — GitHub Actions secrets, не hardcoded значения в workflow-файлах.
- Если токен скомпрометирован — считать его протухшим: он живёт год и виден всем, у кого будет
  доступ к git-истории или бэкапу HA. Проще всего — зайти на `/login` сервиса и пройти push-auth
  флоу заново, старое состояние `/settings` → "Выйти" сотрёт прежний токен.
